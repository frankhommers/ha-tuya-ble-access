# Tuya BLE Access 0.3.3

Configured locks now have an optional **Bluetooth proxy** selector. **Automatic**
keeps Home Assistant's routing; selecting an adapter/proxy enforces that source
for this lock. The selection persists across restarts, and the control remains
usable when the lock or selected proxy is offline. Switch back to Automatic to
remove the restriction. Initial discovery and activation still use automatic routing.

A fixed route deliberately does not fall back to another proxy. HA's client path
selection is overridden for this client only; its slot accounting and connection
lifecycle remain in place. This uses protected HA hooks and fails closed if they
are unavailable. Future HA versions may need a compatibility update.

**Refresh status locally** now bypasses the automatic polling cooldown and
reports connection failures instead of silently returning cached state.

Reloading the integration now cancels and awaits pending connection attempts.
Event collection and notification tasks are tied to the config entry lifecycle
so an old instance cannot keep reconnecting after replacement.

## Validation and limits

- Regression tests cover route isolation, absent/full proxies, unsupported HA,
  offline selection recovery, refresh errors, persistence, and cancellation of
  running and queued connects.
- Routing was checked with the real Home Assistant 2026.8.3 Bluetooth wrapper in
  an isolated container; no live Bluetooth connection was made by that test.
- Production logs showed connection timeouts through the selected GL-S10,
  including after waking the lock. This release is not yet verified to resolve
  that physical connection problem. Pinning alone cannot fix an unreachable lock.
- Credential pause/resume is not implemented; hardware support is unverified.
- Existing activation, temporary PIN and other protocol hardware validation
  limits remain unchanged.
