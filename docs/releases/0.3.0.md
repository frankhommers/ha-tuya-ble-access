# Tuya BLE Access 0.3.0

## Cloud-first setup

Previously setup depended on a Bluetooth advertisement before fetching a device's
keys. The account device list also omitted `category`, causing the known K3 to be
rejected as "not a lock". The app obtains categories separately.

Account import now signs in once, enumerates devices across homes, retrieves
`thing.m.device.ref.info.list` product references, joins by exact product ID and
retrieves available Bluetooth keys for recognized locks. No product ID is
invented or used as a default. Explicit non-lock categories remain rejected.
Missing category can only fall back to an exact bundled product profile, never
the generic profile.

An existing hub's Add hub action opens Add a lock, offering account import or
selection from the saved registry. A sleeping or out-of-range lock can be selected
without waiting for discovery. Radio discovery no longer initiates cloud login.
A reset/unbound lock still requires separate explicit reactivation confirmation.

## Persistent local registry

The MAC-indexed `tuya_ble_access_devices_key_history` store retains identities and
key snapshots without automatic expiry. Existing records are backfilled, changed
key generations are preserved, and identical consecutive snapshots deduplicate.
Removing a device does not erase its recovery history. Account passwords and DP
payloads are excluded. Old key sets are never automatically tried or combined.
Keep this private store in your Home Assistant backups.

One device's key failure retains partial information and does not stop importing
other devices. Account-wide operations have a two-minute deadline, with individual
HTTP requests limited to fifteen seconds. Reconfiguration imports the account even
when the hub has no active locks. Unknown/non-lock devices with MAC addresses stay
in the registry but cannot be selected as locks.

retrieved two device records, all required K3 key fields and a successful local
