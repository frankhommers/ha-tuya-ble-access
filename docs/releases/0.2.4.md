# Tuya BLE Access 0.2.4

The GL-S10 received the K3 lock's FD50 service-data advertisement, but Tuya BLE
Access did not match it. The previous manifest matched the FD50 service UUID
list, A201 service data and manufacturer data. The received packet contained
only FD50 service data; it had no service UUID list, manufacturer data or local
name. Thus it appeared in HA's Bluetooth monitor without starting discovery.

## Fix

- Match FD50 service data as well as the existing advertisement formats.
- Read the bound flag from complete V4/V5 FD50 product-ID advertisements. Do not
  rely on the scan-response name `TyOS`, which can be missing or stale.
- An unnamed unbound lock opens the credential-check screen. A bound lock keeps
  the existing import path, even if a cached name still says `TyOS`.
- Short, malformed and unsupported headers do not establish pairing state.

## Evidence and validation

The observed service data was `510c0008626132716b313737` (product `ba2qk177`).
It was replayed through **Home Assistant 2026.8.3's actual IntegrationMatcher**
in a network-isolated container: the 0.2.3 manifest returned no match, and the
corrected manifest matched `tuya_ble_access`.

Regression tests cover the unnamed packet, stale names on bound advertisements,
truncated/unsupported headers and the existing two-stage credential-check flow.
Tuya's [SDK porting guide](https://developer.tuya.com/en/docs/iot-device-dev/Porting-Guide-BLE?id=Kam0xjtz4n6e0)
documents the bind flag for V4; recorded K3 V5 advertisements use the same bit.

A weak radio link can still prevent a subsequent Bluetooth connection. Discovery
matching is verified; physical activation on the production lock remains to be
checked with the lock awake near its proxy.

Update and restart Home Assistant to load the new discovery matcher. No factory
reset or repeated Tuya pairing is required for this update.
