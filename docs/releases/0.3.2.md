# Tuya BLE Access 0.3.2

Bluetooth unlocks started in Home Assistant previously lost their initiating
user's service context. The credential sensor also fell back to the hardware
number **User 1**, even though Bluetooth unlocks have no fingerprint/card/PIN
credential to name.

## HA initiator attribution

The lock entity captures the service context and passes it to the coordinator.
When a matching fresh Bluetooth unlock record arrives, **Last unlocked by** and
history show the HA user's name, with their linked person entity where unique.
An HA command without a user shows **Home Assistant**. Unmatched Bluetooth
reports remain **Bluetooth**, without inventing a person or guessing from an
automation's parent context.

Hardware `user_id` stays distinct from `ha_user_id`. Sensors/history also expose
`context_id`, `parent_id` and `initiator_source`. The credential sensor no longer
shows **User 1** for Bluetooth or other methods without an enrolled credential.
Confirmed identity attributes survive a sensor restore.

Correlation is per lock, starts only immediately before writing the command,
expires after 30 seconds, and requires a Bluetooth event timestamp between the
command timestamp and five seconds later. Overlapping candidates remain
unattributed. Each command can claim one record; old records, status snapshots,
failed/cancelled writes and other unlock methods cannot borrow its identity.
A matching record arriving immediately before motor status is retained once
within a one-second window; a subsequent motor run clears the identity.

The new `tuya_ble_access_bluetooth_unlock` event carries the matched initiator and
original HA context, including when the motor's generic unlock event arrived
first. A command without a physical event does not claim an unlock. Attribution
is a best-effort association with the requester, not proof of the person entering.
Old history is not retroactively attributed; pending requests are not persisted.

## Validation

319 automated tests pass, including successful commands, pending/no event,
connection backlog, duplicate/old/expired records, overlapping users, cancellation,
failed writes, automation contexts and both motor/report orders. Real entity
context forwarding, sensor rendering and restore were checked in an isolated
Home Assistant 2026.8.3 container without network or hardware commands.

Physical attribution still needs checking with the production lock. Existing
V3/V4, activation and temporary PIN hardware validation limits remain unchanged.

Update the integration and restart Home Assistant. Then perform a new unlock
from your own HA login and inspect **Last unlocked by**. No reset or re-pairing
is needed, and existing history remains as originally recorded.
