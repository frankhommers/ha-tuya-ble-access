# Tuya BLE Access 0.3.1

Selecting a saved cloud lock in 0.3.0 could create an active Home Assistant device
even when the physical lock had since been factory reset. Setup now distinguishes
saved pairing details from a verified physical pairing.

## Connection check before adding

- Selecting a saved lock opens **Check the lock connection**, including through
  discovery of a previously saved bound lock. Merely opening it does not connect.
- The check sends only DEVICE_INFO, never PAIR, reset or unlock commands. A paired
  reply must use the saved normal connection security mode before adding a device.
- An unbound reply opens a separate pairing confirmation. A stale cloud record
  or advertisement cannot silently reactivate it.
- Offline, timed-out or unverified locks remain saved without an active device.
  Retry later, or clear **Check the connection now** to finish setup for now.
- On first account setup, an unbound lock first offers to save the account. Reopen
  **Add a lock → Choose a saved lock** to continue to pairing confirmation.
- Concurrently refreshed pairing details must be checked again before adding.
- Ordinary reconnection refuses to send PAIR to an unbound/reset lock, including
  a reset occurring after setup's check.

The check has a 30-second deadline plus up to five seconds for disconnecting. It
shares per-device connection locks with activation and normal operations. A reply
using only activation authentication data does not establish that saved normal
connection details work; setup asks for an explicit Tuya refresh in that case.

Setup uses **pairing details / koppelgegevens** instead of keys / sleutels.
Technical fields in advanced import keep their protocol names. A complete record
is explicitly described as data availability, not proof of a working lock.

## Validation and limits

306 automated tests pass. They cover cloud records with reset hardware, stale advertisements,
separate pairing confirmation, offline retry, deferred first setup, changed data,
connection cleanup/cancellation, encrypted reply security modes and refusal to
pair from ordinary reconnection. Existing activation and cloud inventory checks
remain covered. The actual connection and first-account form schemas and English/Dutch
placeholders were also checked in Home Assistant 2026.8.3 without network access.
No production lock was paired or unlocked during this change.

The new physical check and recovery flow still need validation against the real
lock and Bluetooth proxy. A successful DEVICE_INFO check establishes its current
binding state and acceptance of connection data; it does not test unlocking.
Existing V3/V4 profiles and temporary PIN lifecycle retain their earlier physical
validation limitations. Advanced manual import remains intended for already-bound
locks with previously obtained details.

Update Tuya BLE Access to 0.3.1 and restart Home Assistant. Open the hub's **Add
hub** action, choose a saved lock and check its connection. Do not factory-reset
the lock for this update.
